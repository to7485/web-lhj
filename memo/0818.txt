애플리케이션 배포 환경 구성
1. 소스코드 빌드 과정 이해
빌드 : 소스코드를 실행할 수 있는 상태로 변환하는 과정, 프로그래밍 언어와 유형에 따라 빌드 과정이 다르다
- 컴파일 언어(C, C++ 등)
ㄴ 기계어로 바로 변환되어 실행되기 때문에 가장 속도가 빠르고 보안에 유리하다. 하지만 소스가 변경될 때마다 컴파일 과정을 통해서 빌드 작업을 수행하기 때문에 과정이 오래걸린다.
- 바이트 코드 언어(Java, C# 등)
ㄴ 컴파일의 결과물이 실행 파일이 아닌 'class'라는 바이트 코드 파일로 생성되고 가상 실행 환경인 JRE,CLI에서 한 줄씩 실행하는 방식으로 빌드된다. JRE, CLI 환경에서 실행될 때 기계어로 변환되며, 컴파일 언어에 비해 빌드 과정이 빠르다.
- 인터프리터 언어(JavaScript, Python 등)
ㄴ 컴파일 언어와 다르게 한 줄씩 번역되어 실행된다. 인터프리터 언어는 컴파일하는 과정에서 메모리가 훨씬 적게 소모되고 빠른 시간에 컴파일을 진행할 수 있다.

2. 애플리케이션 배포 환경
배포 : 개발자 또는 사용자가 애플리케이션을 실행, 테스트할 수 있도록 컴파일된 프로그램, 실행에 필요한 리소스(이미지, 환경 설정 파일)를 서버상의 적합한 위치로 이동하는 작업
- 애플리케이션 배포는 해당 애플리케이션의 동작 환경의 영향을 받는다.
- 웹 애플리케이션의 경우 웹 서버, WAS(Web Application Server)를 동작 환경으로 사용한다

웹 서버(Web Server)
- 사용자의 http 요청을 받아 웹 컨테이너에 요청을 전달하고 결과값을 받아와 사용자에게 전송하는 역할을 수행한다.
- 애플리케이션 배포시 이미지, 단순 HTML과 같은 정적인 리소스를 배포하며, 정적 리소스를 빠르고 안정적으로 처리한다.

웹 애플리케이션 서버
- 사용자의 요청을 받아 동적인 처리를 수행하는 프로그램 실행 부분을 배포한다.
- WAS 구성 및 운용을 위한 표준 규격을 정하고 있으며, 제품마다 배포 방식과 설정이 일부 다르다

애플리케이션 배포환경 구성하기
1. 프로젝트 배포 관리 요건을 분석하고 배포 환경 구성 방안을 기획한다
- 프로젝트의 애플리케이션의 기술적인 특성을 확인하고 배포 방식 결정
ㄴ 애플리케이션의 개발 언어 확인
ㄴ 프로젝트에 적용되어 있는 개발 도구, 개발 환경을 확인
ㄴ 애플리케이션의 유형을 확인(모바일, 웹, C/S기반 시스템 등)
ㄴ 배포 대상 리소스의 유형을 확인한다(배포 단위를 파악 : Jar, War, ear 등)
ㄴ 배포 대상 리소스 유형 확인(html, 프로그램, 공통코드를 분류)
ㄴ 배포 시 연계하여 처리하고자 하는 프로젝트 요건을 확인

- 개발하려는 애플리케이션의 인프라 환경을 확인하고 대상 서버를 확인한다
ㄴ 개발하려는 애플리케이션 서버 구성 환경을 확인한다
ㄴ 리소스 유형별 배포 대상 서버를 확인한다
ㄴ 분산 배포 대상을 확인한다
ㄴ 통합 빌드 배포 구성도를 작성한다

2. 애플리케이션 배포를 위한 도구와 시스템을 선정한다
- 소스 형상관리 도구를 선정한다
ㄴ 일반적으로 애플리케이션 개발 기간 중에는 일시적인 사용과 비용 측면을 고려하여 오픈소스 기반의 형상관리 도구(Maven, CVS, Subversion 등)를 사용하고, 배포 이후 운영 환경에서는 안정적인 운영을 위해 상용 형상관리 도구를 도입하여 사용한다.
- 빌드 도구를 선정한다
ㄴ 애플리케이션 빌드, 배포 스크립트 작성을 위한 빌드 도구를 선정한다.
ㄴ 빌드 도구는 일반적으로 도입된 개발 도구상에 임베디드 되어 제공되는데, 프로젝트 차원의 전체적인 통합 빌드 수행을 위해서는 별도의 빌드 도구를 사용해야 한다.
ㄴ 개발 언어, 개발 도구별로 표준적으로 사용하는 빌드 도구가 정의되어 있으며, 해당 기준에 맞추어서 빌드 도구를 선정한다(Java는 Eclipse를 사용한다)

- 빌드 스케줄 관리 도구를 선정한다
ㄴ 지속적인 통합, 빌드 환경의 구성이 필요한 경우 빌드 스케줄 도구를 사용한다.
ㄴ 빌드 스케줄 도구도 빌드 도구에 맞추어서 표준적으로 사용되는 도구가 있으며, 해당 도구를 선정한다.

- 테스트 도구를 선정한다
ㄴ 자동화된 테스트 수행이 필요한 경우 테스트 도구를 선정한다
ㄴ 테스트 도구 선정 시에는 해당 테스트 도구가 사용하는 빌드 도구, 형상관리 도구와 연계가 가능한지, 호환성을 제공하는 버전인지 확인한다.
ㄴ 테스트 도구는 테스트 대상별로 여러 유형이 존재하며, 반영하고자 하는 범위 내에서 선정한다.

- 검토 대상 코드 인스펙션 점검 도구를 파악한다
ㄴ 발주사 또는 운영중인 시스템에서 사용 중인 코드 인스펙션 점검 도구가 있거나 RFP상에 명시된 도구가 있다면, 해당 도구를 우선적으로 사용할 수 있는지 확인한다.

- 애플리케이션 개발에 적합한 코드 인스펙션 도구를 선정한다
ㄴ 오픈소스 기반의 도구를 사용하고자 하는 경우에는 해당 도구의 기술 지원이 가능한 인력의 존재 여부를 판단해야 한다
ㄴ 상용 제품을 도입하는 경우 프로젝트 기간 중 적절한 지원이 가능하도록 기술 지원 사항을 포함하여 선정한다.

애플리케이션 배포 환경 설정
1. 애플리케이션 배포 단위
- jar(Java Archive)
ㄴ Java 라이브러리, 리소스, property 파일들을 포함한다.
ㄴ 프로그램에서 참조하는 라이브러리, 구현된 비즈니스 서비스를 배포할 때 jar 단위로 패키징하여 배포한다.
- war(Web Archive)
ㄴ 웹 컨테이너에 배포되는 배포 형식으로 Service, jar 파일과 WEB-INF 폴더에 들어있는 web.xml 파일로 구성.
ㄴ 웹 컨테이너상에 배포되어 독립적인 UI단 웹 애플리케이션 서비스를 제공할 수 있다.

- ear(Enterprise Archive)
ㄴ jar와 war를 묶어서 하나의 완성된 웹 애플리케이션 서비스를 제공할 수 있다.

2. 형상관리 시스템
서비스 제공 대상 형상 항목을 식별하여 기준선을 설정하고, 형상 항목 변경 과정에서 점검, 검증 등의 체계적인 통제를 통해 형상 항목 간의 일관성과 추적성을 확보하기 위한 시스템

- 형상관리의 범위
ㄴ 신규 프로젝트 및 보완 개발, 업무 시스템의 운영/유지보수, 전산 설비 및 시스템 소프트웨어 등과 관련된 작업, 사용자 파일 관리 등을 포함한다.

- 형상관리 시스템에서 사용하는 용어
ㄴ 형상관리 : 소프트웨어의 전체 생명 주기의 관리
ㄴ 형상항목 : 형상관리 대상이 되는 항목
ㄴ 기준선 : 공식적으로 검토되고 협의되어 향후 기준이 되는 형상 항목의 집합체
ㄴ 마이그레이션 : 개발 완료된 시스템이 운영 단계로 전환될 때 관련 소스 파일을 저장 공간으로 이관시키는 잘업
ㄴ 리포지터리 : 관리 대상을 형상관리 시스템으로 일괄 전송하여 압축, 암호화한 후에 저장, 관리하는 저장 공간
ㄴ 워크플로 : 형상관리 활동을 수행하기 위해 미리 정해진 절차가 형상관리 시스템 안에 구현되어 있는 것

1.
A : JAR - Java 프로그램, 라이브러리 및 리소스를 하나의 파일로 묶는 데 사용하며 Springboot와 같이 독립적으로 실행되는 프로그램에서 사용
B : WAR - JSP, Servlet, Java Class, WEB-INF 등으로 구성된 웹 애플리케이션을 Tomcat과 같은 웹 컨테이너에 배포할 때 사용
C : EAR - 여러 JAR와 WAR 등의 모듈을 하나의 엔터프라이즈 애플리케이션 단위로 구성할 때 사용한다.

기준선은 공식적으로 검토,협의되어 앞으로의 기준으로 사용하는 상태이므로 이후 변경도 해당 기준을 중심으로 관리해야 한다.

레파지토리에서는 관리 대상의 여러 버전과 변경 정보를 저장,관리 할 수 있다.

5.

적절하지 않다 서버에 설치한 뒤에도 프로그램 정상 기동, 연결 URL 접속, 관리자 로그인, 주요 기능 정상 작동을 확인해야 한다.

개발자의 PC에는 필요한 Agent 도는 플러그인 등을 동일하게 설치해야 하며 주요 설치 오류에 대한 조치가이드도 제공해야 한다.

서버단은 여러 개발자가 공동으로 사용하는 서버 환경이고, 클라이언트단은 개발자 개개인의 PC 환경이다.

6.
A : 긴급 적용 - 장애,오류로 신속한 조치가 필요한 경우이며 최소한의 확인을 거쳐 빠르게 적용한다
B : 일반 적용 - 개발,수정 프로그램을 일반적인 검토,테스트, 승인 절차를 거쳐 적용한다.
C : 통합 빌드 - 일정 기간 동안 변경된 전체 개발 내역을 취합하여 전체 소스를 빌드,배포하고 상태를 점검하는 활동

개발자가 수정한 내용에 오류가 있으면 기존 장애가 해결되지 않거나 새로운 장애가 발생할 수 있다.

단일 프로그램 배포가 특정 기능이나 파일의 변경사항을 적용하는 것이라면, 통합 빌드는 프로젝트 전체 개발 내역을 대상으로 전체 시스템의 정상 상태를 점검한다는 점에서 차이가 있다.

7.
소스를 수정한 후 정식 배포 요청, 검토, 승인 절차를 거치지 않고 자신만의 판단으로 운영 서버에 직접 배포하였다.

개발자 소스 체크아웃 -> 프포그램 개발 및 수정 -> 개발자 테스트 -> 소스 체크인 -> 테스트 배포 요청 -> 수행사 PL의 배포 요청 검토 -> 고객사 PL의 배포 승인 -> 빌드,배포 관리자의 테스트 환경 배포 -> 배포 결과 및 정상 동작 확인

운영 환경은 실제 사용자가 서비스를 이용하는 환경이므로 잘못된 프로그램이 배포될 경우 실제 업무 장애로 이어질 수 있다.

관리 절차가 없으면 장애 발생 시 누가 어떤 파일을 언제 배포했는지 알기 어렵고, 잘못된 버전의 배포나 승인되지 않은 변경이 운영 서버에 적용될 수 있다.

8.
A : 배포 관리자
B : PM/PL
C : 개발자

배포업무는 개발자 혼자 수행하는 작업이 아니닫
배포 관리자는 빌드,배포 환경과 실제 배포를 관리하고, PM/PL은 결과 및 진행 상태를 검토하며, 개발자는 개발,테스트, 오류 수정 등을 담당한다

역할과 책임을 구분하면 승인, 검토, 실제 배포 작업의 책임 소재를 명확하게 할 수 있다.

1.
두 코드 모두 실행 자체에는 문제가 없을 수 있지만 프로젝트에서 정한 작성 규칙과 보안 규칙을 위반하므로 정상적인 코드라고 판단하기 어렵다.

코드 인스펙션을 통해 확인할 수 있다.

코드 인스펙션은 프로그램을 실제로 실행하여 결과를 확인하는 것이 아니라, 사전에 정의된 RULE을 기준으로 소스코드를 분석하여 규칙 위반이나 문제 가능성이 있는 코드를 찾아내는 정적 테스트 방식이다

2.
A : 성능 개선 - count는 선언만 하고 사용하지 않는 미사용 변수이기 때문에
B : 코드 작성 규칙 - 프로젝트에서 정한 클래스 명명 규칙을 위반
C : 에러 발생 가능성 - null 상태의 객체에서 length()를 호출하므로 실행 중 오류가 발생할 가능성이 있다.

미사용 변수는 프로그램을 즉시 중단시키지는 않더라도 불필요한 코드를 증가시키고 소스코드의 효율성, 가독성 및 유지보수에 영향을 줄 수 있다.

3.
A : Blocker
B : Critical
C : Major
D : Minor
E : Info.

가장 우선적으로 수정해야 하는 것은 A의 Blocker이다
Blocker는 에러 발생 가능성이 매우 높거나 메모리 누수 등과 같이 심각한 문제를 일으킬 수 있는 항목으로 반드시 수정해야 하는 위반사항이다

모든 위반 사항이 시스템에 미치는 영향이 동일하지 않기 때문이다.
위험도와 영향에 따라 심각도를 구분하여 관리해야한다.

4.
수천 개의 소스코드를 사람이 직접 확인하면 많은 시간과 인력이 필요하며 동일한 규칙을 반복해서 검사해야 하기 때문이다

정규 표현식을 이용하여 코드 인스펙션 Rule을 작성하고 자동으로 검사할 수 있다.

^ : 문자열이나 행의 처음
$ : 문자열이나 행의 끝
[] : 괄호 안에 지정된 문자 중 하나
* : 앞의 내용이 0회 이상 반복
{m,n} : 앞의 내용이 m회 이상, n회 이하 반복

^user : user로 시작하는 문자열
Service$ : Service로 끝나는 문자열

5.
코드 인스펙션 도구가 기본적으로 제공하는 Rule에 없더라도 프로젝트 개발 표준이나 회사 보안 정책에서 요구하는 사항이라면 추가적으로 검사해야 한다

프로젝트 개발 표준과 기본 Rule을 비교한 후 부족한 Rule을 확인하여 프로젝트 전용 Rule을 추가하거나 기존 Rule을 수정해야 한다.

변경될 가능성이 있거나 외부에서 관리해야 할 값을 소스코드에 직접 작성하는 것을 하드코딩이라고 한다.

서버 주소 변경 시 소스코드를 직접 수정해야 한다
비밀번호가 소스코드에 노출될 수 있다
환경별 설정 변경이 어려워질 수 있다
보안 관리가 어려워질 수 있다
유지보수가 어려워 질 수 있다

프로젝트마다 개발 표준과 보안정책이 다를 수 있기 때문에

6.
A : 개발자가 개발 과정에서 자신이 작성하거나 수정한 특정 소스에 대해 수행하는 개별 점검
- 개발 과정에서 문제를 빠르게 확인하고 수정하기 위한 목적

B : 애플리케이션을 서버에 배포하기 전에 수행하는 배포 단계의 사전 점검
- 배포 전에 코드 작성 규칙 위반이나 오류 가능성을 발견하여 수정하는 것이 목적

C : 코드 인스펙션 담당자가 전체 프로젝트의 소스를 대상으로 일정 주기마다 수행하는 사후 일괄 점검이다
- 프로젝트 전체의 코드 품질과 규칙 준수 상태를 주기적으로 확인하기 위한 것

적절하지 않다
개발이 거의 종료된 시점에서 처음 코드 인스펙션을 수행하면 잘못된 코딩 방식이나 규칙 위반이 이미 수많은 소스에 반복되어 있을 수 있다
그 결과 수정해야 하는 코드가 매우 많아지고 수정 비용과 시간이 증가할 수 있다.

개발자의 잘못된 코딩 습관이나 프로젝트 규칙 위반을 초기에 발견할 수 있다. 문제를 조기에 발견하여 반복적인 오류의 확산과 수정 비용을 줄일 수 있다

7.
운영 서버에 프로그램을 먼저 배포한 뒤 코드 인스펙션을 수행한다는 점
코드에 문제가 있는 상태로 운영 서버에 배포되면 실제 사용자에게 장애가 발생할 수 있다.

개발 완료 -> check in -> 코드 인스펙션 -> Rule위반 확인 -> 문제 여부 판단 -> 문제 있으면 -> 개발자 수정 -> 다시 점검
       -> 문제 없음 -> 빌드 배포 진행

Rule 위반 사항이 발견되었다면 해당 내용을 개발자에게 전달하여 수정하도록 해야 한다.
특히 배포 기준상 반드시 수정해야 하는 위반 사항이 있다면 수정 및 재점검이 완료되기 전까지 배포를 진행해서는 안된다.

코드 인스펙션의 목적은 프로그램을 배포한 후 문제가 발생했을 때 찾는 것이 아니라 배포 전에 오류 가능성이나 규칙 위반을 발견하여 수정하는 것

8.
적절하지 않다.
개발자가 프로그램을 수정하고 시다는 이유만으로 형상관리 서버에서 소스를 임의로 Check Out해서는 안된다.
먼저 변경 대상과 변경 이유, 일정 및 영향 범위를 확인하고 관리자의 승인을 받아야 한다

개편 계획서를 작성하고 관리자의 승인을 받아야 한다.

- 무엇을 수정하는가
- 왜 수정하는가
- 언제 수정하는가
- 어떤 프로그램에 영향을 미치는가
- 변경 대상 프로그램
- 개편 일정

개발자가 형상관리 대상 소스를 임의로 변경하는 것을 방지하고, 변경으로 인해 다른 프로그램에 문제가 발생하는지를 사전에 확인하기 위해서

9.
과거 버전을 기준으로 개발했다는 것
변경 작업은 형상관리 서버에서 정확한 대상과 최종 버전을 확인한 후 수행해야 한다.

v2.1을 기준으로 새로운 프로그램을 작성하면 v2.2와 v2.3에서 이미 반영된 변경 사항이 사라질 수 있다.

변경하려는 프로그램이 정확한 대상인지
형상관리 서버의 현재 최종 버전이 무엇인지
해당 버전이 현재 운영, 개발 기준과 일치하는지

정식 반출 절차
프로그램 변경 필요 -> 개편 계획서 작성 -> 관리자 승인 -> 변경 대상 식별 -> 반출 의뢰서 작성 -> 관리자 승인 -> 형상관리자에게 반출 요청 -> 최종 버전 확인 -> Check out -> 개발자 수정

10.
변경 영향분석을 안함
개편 계획서 작성하지 않음
관리자가 승인하지 않음
변경 대상 형상 항목을 정식으로 식별하지 않음
반출 의뢰서를 작성하지 않음
반출에 대한 관리자 승인을 받지 않음
형상관리자를 통한 정식 반출 절차를 거치지 않음
최종 버전을 확인하지 않음
코드 인스펙션을 실행하지 않음
소스 검증 없이 빌드, 운영, 배포를진행하려고 했다.

프로그램 변경 필요 확인 -> 변경 대상 및 영향 분석 -> 개편 계획서 작성 -> 관리자 검토 및 승인 -> 변경 대상 형상 항목 식별 -> 반출 의뢰서 작성 -> 관리자 승인 -> 형상관리자에게 반출 요청 -> 정확한 대상 및 최종 버전 확인 -> Chect Out -> 개발자 수정 -> 개발자 테스트 -> Check IN -> 코드 인스펙션 -> Rule 위반 확인 
-> 위반 있으면 -> 개발자 수정 및 재확인
->위반 없으면 -> Build 진행
