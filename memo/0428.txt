데이터 모델링
- 현실 세계의 업무 내용을 데이터베이스에 저장할 수 있도록 데이터 구조로 설계하는 과정

모델링 필요한 이유
이상현상의 발생을 막아야 한다.
1. 데이터 중복이 발생할 수 있다.
2. 갱신 이상 -> 같은 정보가 여러개 저장되어 있을 때 전부 수정하지 않아서 데이터의 불일치가 일어나는 현상
3. 삭제 이상 -> 필요 없는 데이터를 지우려다 필요한 데이터까지 삭제하는 경우
4. 삽입 이상 -> 필요한 데이터를 추가하려다 필요없는 데이터까지 추가하는 경우

데이터 모델링 과정
1. 요구사항 분석
- 업무에서 어떤 데이터를 관리해야 하는지 파악하는 단계
- 주요 명사를 찾아서 -> 엔티티로 만든다.

2. 개념적 모델링
- 업무 내용을 큰 그림으로 표현하는 단계이다.
- 주로 ERD를 사용한다.

주요 구성 요소
엔티티(Entity) : 관리해야 할 대상
속성(attribute) : 엔티티가 가진 정보
관계(Relationship) : 엔티티 간 연결
식별자(Identifier) : 데이터를 구분하는 값

엔티티 간 관계 설정
- 관계를 문장으로 처리
학생은 수강신청을 한다.
수업은 수강신청을 받는다.
강사는 수업을 담당한다.

관계 차수 정하기
1:1, 1:N, M:N중 어떤 관계인지 정한다.

학생 1명은 여러 수강신청을 할 수 있다. -> 학생 1 : 수강신청 N
수업 1개는 여러 수강신청을 받을 수 있다. -> 수업 1 : 수강신청 N
강사 1명은 여러 수업을 담당할 수 있다. -> 강사 1 : 수업 N

학생 N : 수업 M
실제 설계에서는 중간 엔티티인 수강신청으로 풀어준다.
학생 1 : N 수강신청 N : 1 수업

논리 모델링
- 개념적 모델을 실제 테이블 구조에 가깝게 바꾸는 단계
- ERD를 가지고 테이블을 설계
- 테이블의 이름이나 속성의 이름을 정하는 단계
- 제약조건(PK,FK 등...), 정규화

정규화
실무에서는 보통 3차까지 다룸 -> 더 하면 오히려 조회속도가 느려짐

제1정규형(1NF) -> 속성 하나에는 하나의 값만 들어가야 한다.

BCNF(Boyce-Codd Normal Form)

※후보키 : PK가 될 수 있는 속성

모든 내용을 조회하고 싶다.

LIKE
- 문자열 안에서 특정 글자나 패턴을 찾을 때 사용하는 조건문
SELECT 컬럼명
FROM 테이블명
WHERE 컬럼명 LIKE '패턴'

SELECT * FROM FILM WHERE TITLE = 'LOVE'
- 이 SQL은 제목이 정확히 LOVE인 영화만 찾는다.

LIKE는 포함 여부, 시작 문자, 끝 문자, 특정 글자 패턴을 찾을 수 있다.

% : 글자 수와 상관 없이 아무 문자나 여러 개 올 수 있다는 뜻

'A%' : A로 시작하는 데이터
'%A' : A로 끝나는 데이터
'%A%' : A를 포함하고 있는 데이터
'A%B' : A로 시작하고 B로 끝나는 값

_ : 문자 1개를 의미한다.

'A_' : A로 시작하고 전체 길이가 2인 값
'A__' : A로 시작하고 전체 길이가 3인 값
'_A': A로 끝나는 전체 길이가 2인 값
'_A_': 전체 길이가 3이고 A가 가운데 있는 값

DCL(Data Control Language) : 데이터 제어어
- 데이터베이스에서 사용자 권한을 관리하는 SQL이다.
GRANT : 권한을 부여
REVOKE : 권한을 회수

DCL이 필요한 이유
- 모든 사용자에게 모든 권한을 주면 위험해진다.

MySQL에서는 사용자를 다음과 같이 구분한다.
'사용자명'@'접속자위치'
'teacher'@'localhost'

사용자 생성하는법
create user '사용자명'@'접속자위치'
identified by '비밀번호';
