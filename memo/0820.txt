애플리케이션 빌드 실행
1. 지속적인 통합(CI : Continuous Integration) 환경
- 개발 과정 중 지속적으로 개발된 프로그램을 통합, 빌드, 배포하여 애플리케이션 개발 내역 검증, 테스트 할 수 있는 환경
- 통합 빌드 과정 중 테스트 도구, 소스코드 품질 측정 도구 등과 연계할 수 있으며, 자동화된 스케줄 관리를 통해서 지속적이고 반복적인 프로그램 빌드, 테스트를 진행할 수 있다.

빌드 도구
- 애플리케이션의 배포 단위, 형식에 따라 소스코드 컴파일, 패키징, 배포하는 스크립트를 제공하고 수행하는 도구
- Ant, Maven, Gradle

테스트 도구
- 개발된 소스코드를 테스트할 수 있는 테스트 코드를 작성, 동작 시킬 수 있는 도구로 통합 빌드 수행 시 연결할 수 있다.
- JUnit, DBUnit

소스코드 품질 측정 도구(코드 인스펙션)
- 정해진 소스코드 작성 규칙에 따라 소스코드를 점검하고 규칙 위반 여부를 체크하는 도구로, 통합 빌드 수행시 연결할 수 있다.

테스트 커버리지 측정 도구
- 소스코드 내 테스트가 가능한 경로 중 테스트 도구를 통해서 테스트된 커버리지를 측정하는 도구이다.

빌드 스케줄 관리 도구
- 작성된 빌드 스크립트를 정해진 조건, 시간에 기동하고 진행 상태, 수행 결과를 관리하는 도구

2. 테스트 커버리지
- 전체 프로그램의 범위 대비 테스트 수행 시 해당 테스트 수행을 위해 동작된 프로그램의 범위 비율을 의미

라인 커버리지(구문 커버리지)
- 개발 소스의 각 라인이 수행되었는지를 확인하는 측정 지표이다

분기 커버리지
- 개발 소스의 각 분기문이 수행되었는지를 확인하는 측정 지표이다.
- 만약 소스 내에 if문에 대한 true/false 조건이 있다면 두 가지 모두 테스트되어야 100%로 측정한다

조건 커버리지
- 각 분기문 내에 존재하는 조건식이 모두 테스트 되었는지를 확인하는 측정 지표이다.

애플리케이션 빌드 실행하기
1. 애플리케이션 빌드 스크립트 작성을 위한 빌드 단위 정의
- 애플리케이션 리소스 중 설치되는 부분과 배포되는 부분을 분리한다
ㄴ 설치를 통해 반영되는 부분(프레임워크 설치, 애플리케이션 설정)과 애플리케이션 배포 시 변경되는 부분(프로그램, 이미지, 파일 등)을 구분한다.

- 애플리케이션 배포를 위해서 공통적으로 우선 배포되어야 하는 부분을 분리한다
ㄴ 모든 프로그램에서 공통적으로 참조하는 라이브러리 또는 공통 모듈이 있는 경우 해당 부분을 별도로 분리한다
ㄴ 라이브러리 또는 공통 모듈은 애플리케이션 배포 시 우선적으로 배포되어야 배포 후에 프로그램 오류를 예방할 수 있다.

- 업무 모듈에 따라서 애플리케이션 배포 단위를 정의한다.
ㄴ 애플리케이션의 내부 업무 구분 단위에 따라서 애플리케이션 배포 단위를 세분화 한다.
ㄴ 각 프로그램별 배포도 가능하지만, 업무 기능 단위, 전체 애플리케이션별로도 배포를 수행할 수 있어야 한다.

- 다수 서버에 동시 배포해야 하는 배포 작업을 정의한다
ㄴ 화면 또는 전문 정보와 같은 리소스를 동시에 여러 서버에 배포해야 하는 작업을 구분한다.
ㄴ 동시 배포하는 작업에 대해서 단시간 내 신뢰성 있는 배포 작업이 필요한 경우 해당 기능에 대해서는 기능 구현 및 검증이 진행되어야 한다

- 빌드 수행 시 버전 규칙을 정의한다
ㄴ 빌드 수행 시마다 해당 빌드 버전에 해당하는 버전을 결정하는 규칙을 정의한다.
- 일반적으로 릴리즈 버전, 개발 버전을 분리하고 Major, Minor, BugFix 유형을 구분하여 버전체계를 정의한다.

2. 애플리케이션 빌드 절차에 따라 빌드 스크립트 작성
- 정해진 빌드 단위에 따라 빌드 스크립트를 작성한다
ㄴ 선정된 빌드 도구의 작성 기준, 작성 단위에 따라서 빌드 스크립트를 작성한다.
ㄴ 전체 애플리케이션 관점에서통합, 전체 빌드가 필요한 경우에 작성되며, 개발자별 개별적인 빌드는 개발 도구에 내장된 빌드 도구를 사용한다.

- 코드 인스펙션 도구를 빌드 스크립트에 연계한다
ㄴ 빌드 스크립트에서 코드 인스펙션 연계 태그를 사용해서 코드 인스펙션 도구를 연결한다

- 테스트 도구를 빌드 스크립트에 연계한다
ㄴ 빌드 스크립트에서 테스트 도구 연계 태그를 사용해서 테스트 도구를 연결한다
ㄴ 상용 제품을 사용하거나 선정된 빌드 도구에 따라서 연결 방식, 호환되는 버전이 상이하므로 사전에 연결 방법, 호환성을 확인한 후 연계한다

- 테스트 커버리지 측정 도구를 빌드 스크립트에 연계한다
ㄴ 테스트 커버리지 측정 도구의 경우, 소스코드 컴파일 시 해당 도구의 라이브러리를 참조하여 분석 로그를 남기게 되므로 컴파일 부분과 결과 리포팅 부분을 구분하여 작성한다.

- 빌드 스케줄러 관리 도구를 설정한다
ㄴ 빌드 스케줄러 설정을 통해서 자동화된 CI 환경을 구성할 수 있다.
ㄴ 빌드 스케줄러 도구는 일반적으로 별도의 웹 페이지를 갖고 있으며, 설치 및 기동 후 해당 웹페이지에 들어가서 해당 애플리케이션 개발 시 소스 형상관리 도구, 빌드 도구를 연결하여 빌드, 배포 작업을 설정하고 스케줄링한다

애플리케이션 실행 검증
1. 빌드 스케줄 관리 도구
- 빌드 스케줄 관리 도구의 구성
ㄴ 별도의 웹 애플리케이션으로 구성되어 웹 서버상에 배포되고, 관리자 화면을 통해서 빌드 스크립트, 형상관리 도구 등과 연계되며, 이메일을 통해서 관련 개발자, 관리자들에게 빌드 수행 결과를 제공한다

- 빌드 스케줄 관리 도구의 기능
ㄴ 빌드 작업 스케줄링: 작업 주기, 시간 설정
ㄴ 빌드 작업 상태 및 이력 관리: 대기, 진행, 완료, 오류
ㄴ 빌드 도구 연계 관리 
ㄴ 빌드 수행 결과 리포팅

애플리케이션 실행 검증하기
1. 작성한 빌드 스크립트를 활용하여 애플리케이션 빌드를 수행하고 결과를 확인한다.
- 개발자별 애플리케이션 빌드를 수행한다
- 애플리케이션 전체 통합 빌드를 수행한다
- 빌드 결과를 확인한다
- 빌드 중 수행된 테스트 수행 결과를 확인한다
- 빌드 중 수행된 테스트 커버리지 결과를 확인한다
- 빌드 중 수행된 코드 인스펙션 점검 결과를 확인한다

2. 빌드 중 발생된 오류 사항을 확인하고 대응한다.
- 빌드 중 발생된 오류 사항을 확인하고 원인을 분석한다
- 오류 사항을 확인하고 대응한다

개발자가 체크아웃한 소스가 남아있는 경우
- 빌드 작업 수행 전에 대상 소스를 모두 체크인 하도록한다

빌드 대상 소스코드 간 상호 참조가 발생되는 경우
- 업무 모듈, 공통 모듈의 호출 기준을 정의하여 모듈 간 상호 참조 발생을 방지한다

공통 파일, 환경 설정 파일에 대한 오류
- 빌드 담당자가 빌드 작업 수행 전에 공통 파일, 환경 설정 파일을 업데이트 하도록 한다

컴파일 자체 오류가 발생되는 경우
- 개발자가 개발을 완료하지 않고 체크인을 하거나 개발 표준을 미인지하여 컴파일이 불가능한 경우로 해당 개발자에게 즉시 오류 수정 요청을 한다.

구문 커버리지

조건 커버리지

빌드 스크립트를 사용하면 모든 개발자와 빌드 서버에서 동일한 순서와 기준으로 빌드할 수 있다

9.
형상관리 시스템 -> 소스/버전 관리
빌드 스케줄러 -> 실행 시섬, 조건 관리
빌드 툴 -> 실제 컴파일 패키징
테스트 툴 -> 자동 테스트
코드 인스펙션 툴 -> 소스 품질검사
커버리지 툴 -> 테스트 실행 범위 수집
리포팅 기능 -> 결과 공유

동일하지 않다
빌드 스케줄러 -> 언제 어떤 빌드를 실행할 것인지 관리
빌드 툴 -> 실제 컴파일 테스트 패키징 등의 빌드 작업을 수행
빌드 스크립트 -> 어떤 작업을 어떤 수서로 수행할지 정의

테스트가 성공했더라도 프로그램 전체가 충분히 테스트 되었다는 의미는 아니다
커버리지를 수집하면 전체 코드 중 실제 테스트 과정에서 어느정도가 실행되었는지 알 수 있다.

개발자가 소스를 변경할 때마다 사람이 각 도구를 따로 실행하지 않아도 통합, 빌드, 테스트, 품질검사, 결과 확인을 할 수 있으므로 CI를 반복적으로 운영하기 쉬워진다.

10.
적절하지 않다
도구를 변경할 경우 도구와의 버전 호환성을 확인해야 한다.

새 Ant 버전과 현재 사용중인 JUnit 또는 다른 연계 도구의 버전이 호환되지 않아 테스트 실행이 실패했을 가능성이 있다.

각 도구 조합이 정상적으로 연계되는지 확인해야 한다

기존의 도구들과 호환이 안될 수 있다.
최신 여부보다 프로젝트 전체 환경에서 정상적으로 연계되는지가 중요하다

11.
빌드 스케줄러 관리 도구는 빌드 작업의 실행부터 결과 확인까지 관리할 수 있다.

빌드 작업 스케줄링
빌드 작업 상태 및 이력 관리
빌드 도구 연계 관리
빌드 수행 결과 리포팅

실패상태로 판단해야 한다.
컴파일은 성공했지만 JUnit 2건 실패, Critial 1건 존재

개발자가 빌드 서버를 계속 확인하지 않아도 문제 발생 시 사실을 빠르게 알 수 있다.

12.
전체 시스템에서는 서로 다른 모듈들이 연결되므로 라이브러리 버전 충돌, 모듈 간 참조 관계, 인터페이스, 전체 환경 설정에서 문제가 발생할 수 있다.

전체 통합 빌드를 수행해야 한다

개별 빌드
- 대상 : 개발자 또는 개별 모듈
- 목적 : 자신의 개발 결과 정상 여부 확인
- 범위 : 비교적 작음
- 개발자가 수시로 수행 가능

통합빌드
- 대상 : 전체 애플리케이션
- 목적 : 전체 통합 상태 진척, 품질 검증
- 범위 : 전체 시스템
- 스케줄러 또는 마스터 빌드 스크립트 사용 가능

마스터 빌드 스크립트

13.
결과 파일 생성만으로 최종적으로 판단하는 것은 적절하지 않다
빌드 과정에서 실제로 어떤 단계가 수행되었고 정상 완료되었는지 콘솔과 로그를 함께 확인해야 한다

콘솔
- 프로그램이나 빌드 도구가 현재 작업을 수행하면서 출력하는 실행 정보를 확인하는 영역

로그
- 빌드 과정과 결과를 시간,단계별로 기록한 정보

빌드 자체 결과 : 콘솔/로그
테스트 결과 : 성공/실패
테스트 커버리지 : 테스트가 실행한 코드 범위
코드 인스펙션 : 소스 품질 및 중요 위반 사항

빌드 명령 자체가 성공했더라도 일부 테스트 실패, 커버리지가 매우 낮음, 코드 인스펙션에서 심각한 위반 발생과 같은 상황이 존재할 수 있다.

14.
충분하다고 판단할 수 없다
테스트 100개가 모두 성공했더라도 전체 코드 중 일부만 테스트 했을 가능성이 있다
커버리지가 35%이므로 상당한 코드가 테스트 과정에서 실행되지 않았을 가능성이 있다

커버리지가 낮음 -> 현재 테스트 케이스 검토 -> 테스트되지 않은 부분 확인 -> 다시 테스트 -> 커버리지 재확인

현재는 그대로 진행하면 안된다
Critical이 2건 존재하고 프로젝트 기준에서 Critical은 반드시 수정하도록 정의되어 있기 때문이다
따라서 개발팀에 수정 요청 후 다시 코드 인스펙션을 수행해야 한다

전체 테스트 결과 : 100건 모두 성공
오더서비스 커버리지 : 35%
테스트 케이스 추가 필요
Critical 2건 존재
Major 9건 존재
수정 후 테스트 및 인스펙션 재수행 필요

15.
A : 개발자의 최신 수정본이 리포지토리에 반영되지 않으므로 통합 빌드에서 이전 버전의 오더서비스가 사용될 수 있다.

B : 모듈 A와 B가 서로 호출하는 상호 참조 관계가 발생
C : 소스와 환경 설정 파일의 버전이 일치하지 않는다.
D : 세미콜론이 누락되어 있으므로 컴파일 오류가 발생하여 빌드가 실패할 수 있다

A : 빌드 전 수정 완료된 모든 대상 소스가 체크인 되었는지 확인
B : 업무 모듈과 공통 모듈 등의 호출 방향과 의존 기준을 명확히 정의하여 상호 참조를 방지한다
C : 빌드 수행 전에 공통 파일과 환경 설정 파일을 최신 버전으로 업데이트하고 소스와 일관성이 있는지 확인한다
D : 해당 개발자에게 컴파일 오류 내용을 전달하고 소스를 수정하도록 요청한다

콘솔과 로그의 오류 정보를 확인해야 한다

빌드 담당자가 직접 수정하는 것은 적절하지 않다

빌드 -> 오류 발생 -> 콘솔/로그 확인 -> 오류 위치와 원인 분석 -> 담당 개발자에게 오류 정보 전달 -> 개발자 소스 수정 -> 개발자 Test -> 체크인 -> 리포지토리의 최신화를 확인 -> 다시 빌드 -> 테스트 결과 확인 -> 커버리지 확인 -> 코드 인스펙션 확인 -> 정상 여부를 확인
