1.
범위 : 송신시스템에서 수신시스템까지
테스트 대상
1. 쇼핑몰의 송신 DB
2. ERP의 수신DB
3. 인터페이스 테이블 또는 인터페이스 파일
4. 로그 테이블과 오류 테이블
5. 연계서버 또는 어댑터
ERP,DB만 테스트하면 최종 데이터의 저장 여부만 확인할 수 있다.
쇼핑몰 송신DB에서 데이터가 정상적으로 추출되었는지, 연계 서버가 데이터를 정상적으로 전달하거나 변환했는지, 인터페이스 테이블 또는 파일이 올바르게 생성되었는지 확인할 수 없다

따라서 데이터가 어느 구간에서 누락되거나 변형되었는지 정확하게 파악하기 위해서는 송신 시스템부터 수신시스템까지 전체 연계 과정을 테스트해야 한다

2.
송신 건수와 수신 건수 비교
병원 예약 시스템에서 전송한 예약 데이터 건수와 진료 시스템에서 서 수신한 데이터 건수가 같은지 확인한다
목적은 데이터의 누락 또는 중복 발생 여부를 확인하는 것

송신DB와 수신 DB의 데이터값 비교
예약번호, 환자명, 예약 날짜 담당 의사 등의 데이터 값이 변경되지 않고 정확하게 전달되었는지 확인한다
목적은 데이터 무결성을 검증하는 것

코드 매핑 결과 확인
병원 예약 시스템에서 사용하는 예약 상태 코드가 진료 시스템에서 사용하는 코드로 정확하게 변환되었는지 확인한다.
목적은 코드 변환 오류를 방지하는 것이다.

데이터 타입 및 길이 변환 확인
날짜, 숫자, 문자열 등의 데이터 타입과 길이가 수신 시스템의 규칙에 맞게 변환되는지 확인한다

데이터가 잘리거나 잘못된 형식으로 저장되는 문제를 방지하는것

전송 후 로그 기록 여부 확인
전송 시작 시간, 전송 완료 시간, 처리 결과, 데이터 건수 등이 로그에 기록되는지 확인한다

연계 처리 과정을 추적하고 장애 원인을 분석하기 위함이다

오류 발생 시 재처리 여부 확인
네트워크 장애나 DB 오류로 전송에 실패한 데이터를 자동또는 수동으로 다시 처리할 수 있는지 확인한다
일시적인 장애로 데이터가 영구적으로 누락되는 것을 방지한다

3.
단위테스트는 송신 프로그램, 수신 프로그램, 코드 매핑 등 연계 모듈의 각 구성 요소를 개별적으로 검증하는 테스트

통합테스트는 송신 시스템부터 수신 시스템까지 모든 구성 요소를 연결하여 전체 연계 흐름을 검증하는 테스트

통합테스트의 흐름
송신 DB -> 연계 데이터 생성 -> 데이터 전송 -> 수신 데이터 검증 -> 수신 DB 반영

4.
운영DB는 실제 고객과 업무 데이터가 저장되어 있으므로 테스트 과정에서 데이터가 수정,삭제,중복 등록 되면 실제 업무에 피해가 발생할 수 있다.

또한 비정상 데이터, 중복 PK, 필수값 누락 등의 오류 상황을 운영DB에서 테스트하면 운영 서비스가 중단되거나 데이터의 무결성이 훼손될 수 있다.따라서 테스트용 DB와 테스트용 데이터를 별도로 준비해야 한다

Adapter 설치
연계 서버 설정
테스트용 DB와 테스트용 테이블 생성
테스트용 파일 경로 설정
네트워크 설정
방화벽 및 포트 설정

테스트 환경은 가능한 한 운영 환경과 유사하게 구성해야 한다. 운영체제, DBMS, 네트워크, 서버 사양, 보안 정책, 연계 솔루션 버전, 데이터 규모를 운영 환경과 비슷하게 구성해야 한다
환경이 차이가 크면 테스트에서는 정상적으로 동작했지만 운영 환경에서는 성능 저하나 호환성 오류가 발생할 수 있다

5.
정상 시나리오 테스트
- 정상적인 회원 데이터가 수신 시스템으로 전송되는지 확인
- 회원 코드가 약속된 코드로 정상적으로 매핑되는지 확인
- 수신된 회원 데이터가 수신 DB에 정상적으로 반영되는 지 확인
- 전송 시작 시간, 완료 시간, 처리 결과가 로그에 정상적으로 기록되는지 확지

비정상 테스트 시나리오
- 네트워크 장애를 발생시켜 오류 처리와 재전송 여부를 확인
- DB Lock을 발생시켜 대기, 오류 기록 또는 재전송 여부를 확인
- 연계 서버를 중지하여 관리자 알림과 복구 후 재전송 여부 확인
- 회원번호나 이름과 같은 필수 값을 누락하여 오류 처리 여부를 확인
- 허용된 길이를 초과하는 데이터를 전송하여 오류 처리 여부를 확인

비정상 시나리오 테스트는 실제 운영 중 발생할 수 있는 장애와 잘못된 데이터에 시스템이 정상적으로 대응하는지 확인하기 위해 필요하다
오류가 발생했을 때 로그 기록, 오류 코드 반환, 관리자 알림, 재처리, 롤백 등이 제대로 수행되지 않으면 데이터가 누락되거나 중복되고 업무가 중단될 수 있다

6.
송신데이터가 5000건인데 수신데이터는 4998건으로 2건의 데이터가 누락됐다
로그 기록, 처리 시간, 코드 매핑이 정상이더라도 송신 건수와 수신 건수가 일치하지 않기 때문에 데이터 무결성이 보장되지 않는다

테스트 결과 검증 시 확인해야 하는 항목
- 송신 데이터 건수와 수신 데이터 건수 일치 여부
- 송신 데이터값과 수신 데이터값 일치 여부
- 변환된 코드값의 정확성
- 데이터 타입과 길이 변환 결과
- 오류 코드와 오류 메시지 기록 여부
- 수신 DB 반영 여부

결과 비교를 위해 사용할 수 있는 자료와 도구
- SQL 쿼리
- 로그 파일
- 오류 로그 파일
- 로그 테이블
- 모니터링 대시보드

7.
오류 발견 -> 원인 분석 -> 프로그램 또는 설정 수정 -> 재시험 -> 정상 여부 확인

회귀 테스트는 수정으로 인해 기존에 정상적으로 동작하던 기능에 새로운 문제가 발생하지 않았는지 확인하기 위해 수행한다

반복되는 테스트는 JUnit, Postman, Apache JMeter, Jenkins, Github Actions 등의 도구를 활용하여 자동화 할 수 있다.
CI/CD 파이프라인과 연계하면 프로그램 빌드, 테스트 실행, 결과 수집, 실패 알림, 회귀 테스트를 자동으로 수행할 수 있다.

8.
- 주민등록번호가 그대로 포함되는 문제
ㄴ 개인정보 유출 위험
ㄴ 주민등록번호를 삭제하거나 가상의 데이터로 변경하여 데이터 익명화 수행
- 실제 휴대전화 번호가 그대로 포함된 문제
ㄴ 테스트 참여자가 실제 고객의 연락처를 확인할 수 있다
ㄴ 일부를 마스킹하여 가린다
- 테스트 계정과 운영 계정이 동일한 문제
ㄴ 테스트 작업이 실제 운영 시스템에 영향을 줄 수 있으며, 운영 권한이 노출될 수 있다
ㄴ 운영 계정과 테스트 계정을 분리해야 한다
- 접근 권한이 제한되지 않은 문제
ㄴ 허가되지 않은 사용자가 테스트에 접근할 수 있다.
ㄴ 업무와 역할에 따라 접근 권한을 제한해야 한다
- 데이터가 암호화되지 않은 문제
ㄴ 전송 과정에서 데이터를 가로채면 개인정보를 그대로 확인할 수 있다.
ㄴ HTTPS의 TLS, VPN, SSH 등을 사용하여 전송 구간 암호화 적용

10.
테스트 자동화 도구
- Selenium : 웹 브라우저를 자동으로 제어하는 도구
- JUnit : Java 프로그램의 단위테스트에 사용하는 도구
- Postman : API 테스트에 사용
- Apache JMeter : 동시 요청과 대량 트래픽을 발생시켜 성능을 테스트하는 데 활용
- k6 : 동시 요청과 대량 트래픽을 발생시켜 성능을 테스트하는 데 활용

Contract Testing
- 송신 서비스와 수신 서비스가 미리 약속한 API 규칙을 준수하는지 확인하는 테스트

실시간 로그 및 모니터링에 활용할 수 있는 도구
- ELK Stack : 로그를 수집, 저장, 검색하고 시각화하는 도구
- Prometheus : CPU, 메모리, 네트워크 등의 성능정보 수집
- Grafana : 수집된 정보를 대시보드로 시각화

AL,ML을 활용할 수 있는 작업
- 테스트 케이스 자동 생성
- 테스트 우선순위 추천
- 오류 패턴 분석
- 비정상 데이터 탐지
- 장애 발생 가능성 예측
- 로그 기반 장애 원인 분석

AI나 ML을 활용하면 많은 로그와 테스트 결과를 빠르게 분석할 수 있으며, 사람이 발견하기 어려운 오류 패턴과 비정상 상태를 찾아낼 수 있다.

연계 모듈 테스트 설계
- 송/수신 시스템 간 데이터 전송 및 인터페이스 처리 과정에서 발생 가능한 오류,무결성 위반 등을 검증하기 위해 테스트 케이스를 설계하고, 이를 기반으로 실제 연계 모듈을 시험,검증하는 활동

필요성
- 데이터 무결성 보장
- 업무 연속성 확보
- 성능 및 확장성 검증
- 보안성 검증
- 최신 필요성

연계 모듈 테스트 설계 절차
1. 테스트 범위 및 대상
범위 : 송신 시스템 -> 연계 서버 -> 수신 시스템
대상 : DB, 인터페이스 테이블, 로그/오류 테이블, 응용 프로그램
2. 테스트 케이스 설계
- 송수신 DB 테이블 값 검증, 오류 코드 처리 확인, 전송 후 로그 기록 확인 등을 할 수 있으며, 단위 테스트와 통합테스트로 구분하여 설계할 수 있다.
3. 테스트 환경 구축
- 테스트 환경 구축을 위해  Adapter 설치, 연계 서버 설정, 테스트용 db/테이블 생성, 네트워크 보안 설정 등이 필요하다
4. 테스트 수행
- 설계된 테스트 케이스에 따라 데이터 전송, 오류 유발, 복구 절차 등을 실행한다
정상 시나리오, 비정상 시나리오로 구분하여 실시할 수 있다
5. 테스트 결과 검증 및 기록
- 데이터 건수 일치 여부, 변환된 코드값 확인, 로그 모니터링 값 겁증 등을 하며 결과비교를 위해 sql 쿼리, 로그파일, 모니터링 대시보드를 활용한다
6. 리뷰 및 개선
- 오류 발생 시 원인 분석 및 수정, 재시험을 수행하며, 자동화된 회귀 테스트 체계로 재시험을 수행한다

연계 모듈 테스트 설계 시 유의 사항
1. 데이터 정확성
- 송/수신 db간 값,건수, 포맷 일치를 확인한다
2. 에러 처리
- 예상치 못한 오류 발생 시 로그 기록, 오류 코드 변환, 관리자 알림 체계가 필요하다
3. 보안성
- 테스트 데이터도 개인정보 ,민감정보 포함 가능 시 마스킹, 익명화 처리가 필요하다
4. 성능 검증
- 실시간 연계 대응 및 대용량 배치 환경 각각 테스트를 수행한다
5. 운영 환경 유사성 확보
- 테스트 환경이 최대한 동일해야 한다
6. 자동화 지원
CI/CD 파이프라인과 연계하여 자동 테스트 실행, 결과 대시보드 제공을 할 필요가 있다

최신동향
1. 테스트 자동화 
- Selenium, JUnit, Postman, Apache JMeter, K6등의 자동화 도구를 활용하고 API Gateway 환경에서 Open API 기반 자동 생성 테스트 스크립트를 활용한다
2. 데이터 검증 고도화

데이터 적시성 : 즉각적인 결과 확인이 필요한 업무는 실시간 방식을, 시차 반영이 허용되는 업무는 배치 방식을 선택한다
네트워크 부하 : 처리하려는 데이터의 건수와 크기를 고려하여, 대용량 트랜잭션이 발생할 경우 운영 DB 부하 완화를 위해 배치 처리를 선택한다

전체를 실시간 처리로 선택했을 때 부작용 : 수십만 ~ 수백만 건의 연계 데이터 요청이 순간적으로 몰릴 경우, 운영 DB에 대량의 트랜잭션과 락이 발생하여 DB 성능 저하 및 메모리 부족현상 발생. 또한 네트워크 과부하로 인해 연계 타임아웃 오류가 빈번해지며 전체 서비스 불능 상태에 빠질 수 있다.


8.
데이터 정합성 보장 : 수신된 데이터가 업무db의 스키마 및 업무 규칙을 준수하는지 검증하는 버퍼 역할을 한다. 중간 검증 과정 없이 직접 적재 시 잘못된 포맷이나 코드 값으로 인해 기존 업무 db의 데이터 오염을 초래할 수 있다.
오류 복구 및 트랜잭션 독립성 : 수신측 업무 DB 적재 로직 중 예외가 발생하더라도, 인터페이스 테이블에 원래 전달받은 데이터 원본과 원천 로그가 보존되어 있으므로 원인 분석이 용이하다


9.
추적성을 위한 로그 요소 : 고유 Trace ID를 발급하여 송신 -> 연계 서버 -> 수신 시스템으로 이동하는 전체 흐름 동안 유지하고, 각 단계 별 타임스탬프 및 처리 상태를 함께 기록해야 한다.
SLA 준수 검증 활용 : 로그에 기록된 '송신 시작 시간'과 '수신 시스템 업무 DB 반영 완료 시간' 간의 차이를 분석하여 연계 구간별 지연시간을 측정한다. 속도를 만족하는 지 검증하고, 처리 지연을 유발하는 병목구간을 찾아내어 시스템 구조 개선의 근거로 활용할 수 있다.

10.
동기식 호출의 문제점 : 송신 시스템이 모든 하위 시스템의 처리가 완료될 때까지 대기해야 하므로 사용자 응답속도가 현저히 느려진다.
후속 시스템 중 하나라도 장애가 발생하면 전체 주문 트랜잭션이 실패하는 연쇄 장애가 발생한다.

메시지 큐 기반 비동기 처리의 효과 
- 주문 시스템은 주문 이벤트를 발생한 후 즉시 응답을 완료할 수 있어 시스템 간 결합도가 낮나진다.
- 배송/SMS 시스템에 장애가 발생하더라도 발행된 메시지는 메시지 큐에 안전하게 대기상태로 보관된다. 수신 시스템이 복구된 이후 큐에서 메시지를 순차적으로 꺼내어 처리할 수 있으므로, 데이터 손실이나 서비스 전체 중단 없이 시스템의 가용성과 높은 결함 허용성을 확보할 수 있다.
