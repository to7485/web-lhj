자바 
- 객체 만들 때 new 해서 객체를 메모리에 올리기 위한 공간좀 줘
- GC가 사용되지 않는 객체를 자동으로 메모리에서 제거
- 메모리 오류 위험이 적다
C
- 메모리를 얼마 공간만큼 할당해달라고 직접 요청(함수)
malloc(sizeof(int) * 4)
- free() 함수를 이용해서 메모리에서 해제
- 상대적으로 크다
- 메모리 최적화에 좋다
- 언어자체가 가볍다

메모리 누수 : 메모리를 점유했는데 해제가 안된것

C -> 클래스 / 객체, 상속, 오버로딩, 예외처리 개념이 없음
C++ -> 객체 지향을 지원, new 사용
C# -> C와 C++의 문법적 영향을 받았지만, 실행 방식과 메모리 관리 측면에서는 Java와 상당히 비슷하다

1.
A : 빌드 - 소스코드를 컴파일하고 패키징하여 JAR, WAR 등의 실행 가능한 상태의 결과물을 만드는 과정
B : 배포 - 빌드된 결과물과 실행에 필요한 리소스를 실제 서버 환경으로 이동하여 설정하고 실행하는 과정

빌드가 완료되어 application.jar가 만들어졌더라도 아직 실제 서버에 적용되지 않았다면 사용자는 해당 서비스를 이용할 수 없다

2.
A : C++은 소스코드를 컴파일하여 기계어 형태로 변환하고 생성된 실행 프로그램을 실행한다
B : Java는 .java파일을 컴파일하여  중간 코드인 .class를 생성한 후 JRE와 같은 실행환경에서 실행한다
C : Python은 프로그램 전체를 먼저 기계어 실행 파일로 만드는 방식이 아니라 인터프리터가 코드를 해석하면서 실행하는 방식이다

세 언어는 변환 및 실행 방식이 서로 다르므로 동일한 빌드 절차를 그대로 적용하는 것은 적절하지 않다

3.
A : 전처리
B : 파싱
C : 링킹

전처리는 실제 컴파일 전에 헤더 파일 등의 필요한 내용을 처리한다

파싱은 작성한 코드가 해당 프로그래밍 언어의 문법에 맞는지 분석한다. 따라서 int number =  처럼 문법적으로 완성되지 않은 코드는 이 과정에서 문제가 발견될 수 있다

링킹은 여러 목적 파일 및 라이브러리를 연결하여 최종 실행파일을 생성하는 과정이다

4.
A,B는 HTML,이미지와 같은 정적 리소스이므로 Web Server에서 처리하는 것이 적절하다.
C는 프로그램 로직을 실행하고 DB를 처리해야 하는 동적 요청이므로 WAS가 담당하는 것이 적절하다

Web Server는 HTML, 이미지 등 정적 콘텐츠의 제공을 주로 담당하며, WAS는 비즈니스 로직과 같은 동적 프로그램 처리를 담당한다

5.
A : JAR - Java클래스와 라이브러리, 리소스 등을 묶는 데 사용할 수 있으며 SpringBoot와 같이 독립적으로 실행되는 어플리케이션에서 사용할 수 있다.
B : WAR - JSP, Servlet, Java class 등으로 구성된 웹 어플리케이션을 WAS에 배포할 수 있다.
C : EAR - 여러 엔터프라이즈 어플리케이션 모듈을 하나로 묶는 형식

동일한 Java 계열 기술이라도 프로젝트 구조와 배포환경에 따라 적절한 배포 형태가 달라진다

6.
company-logo.png -> 이미지 -> 웹서버
main.html -> HTML -> 웹서버
inventory.war -> 웹단 프로그램 -> WAR형태로 배포
NightBatch.class -> 배치프로그램 -> 컴파일된 class파일 배포
interface.xml -> 인터페이스 전문 -> xml 형태 배포
framework-config.xml -> 환경, 프레임워크 설정 관련 리소스 -> 정의된 방식에 따라 배포

배포 대상은 파일 유형마다 실행되는 위치와 처리방법이 다르므로 동일한 위치와 방식으로 복사하는 것은 적절하지 않다.

7.
소스가 형상관리 시스템에 등록되기 전에 운영 서버에 직접 배포함
테스트 전에 운영환경에 반영함
개발자 pc와 운영환경 간 결과가 달라질 수 있음
여러 개발자의 변경사항을 일관되게 관리하기 어려움

개발자 코드 변경 -> 형상관리 시스템에 반영 -> 자동 빌드 -> 자동 테스트 -> 문제 확인

CI를 적용하면 코드 변경 시 반복적으로 통합,빌드,테스트를 자동으로 수행하여 문제를 빠르게 발견할 수 있다

8.
신입 개발자의 제안은 적절하지 않다
개발 서버 : 개발 및 기능 확인
테스트 서버 : 통합 및 품질 검증
운영 서버 : 실제 사용자에게 서비스 제공
DR 서버 : 장애나 재해 발생 시 서비스 복구

운영 서버에서 개발을 직접 수행하면 실제 사용자의 서비스에 영향을 줄 수 있고 검증되지 않은 코드가 운영환경에 반영될 수 있다.

장애 발생이나 재해 발생시 서비스를 복구해야 하는 상황에 사용

9.
WAS 1만 v3.0으로 변경하고 WAS 2와 WAS 3는 이전 버전이므로 로드밸런서가 요청을 어느 서버로 전달하는지에 따라 서로 다른 프로그램 결과가 나타날 수 있다.

따라서 여러 서버가 동일한 서비스를 제공한다면 필요한 서버에 동일한 어플리케이션 버전을 배포해야 한다.

배포 후에는 서버별 배포 버전과 정상 동작 여부를 확인해야 한다.

10.
개발자 코드 변경 -> 형상관리 시스템 반영 -> 최신 소스 가져오기 -> 자동 빌드 -> 자동 테스트 -> 배포 파일 생성 -> 테스트 서버 배포 -> 정상 동작 확인 -> 운영 서버 배포

도구 
형상 관리 도구 -> 소스 및 변경 이력 관리
빌드 도구 -> 컴파일, 테스트 연계, 패키징 및 실행 결과물 생성
테스트 도구 -> 프로그램의 정상 여부 검증
배포 도구 -> 빌드 결과물을 서버에 적용

운영 서버 3대는 동일한 서비스를 처리하므로 동일한 버전을 일관되게 배포해야 한다

각 서버는 개발, 테스트, 실제 서비스, 장애 재해 복구라는 점에서 서로 다른 목적을 가진다.
