내외부 연계 모듈 구현하기

통합구현
서로 다른 시스템이나 모듈을 연결하여 데이터를 주고받고 하나의 서비스처럼 동작하도록 만드는 과정

통합구현이 필요한 이유
1. 이기종 시스템 간 데이터 연계 : ERP, 그룹웨어, 모바일, 회계 프로그램 등 다수 시스템의 연결이 필요하다
2. 서비스 확장성 및 재사용성 : 기존 시스템을 유지하면서 API 연결 등을 통해 신규 서비스 확장
3. 운영 효율성 및 데이터 품질 : 한 번 입력된 데이터가 CRM, ERP, 배송 시스템으로 자동 전달되어 중복 입력 방지
4. 신규 서비스 창출 : 축적된 데이터를 활용해 AI 추천, 맞춤형 광고 등 차세대 서비스 구축

통합 구현의 주요 기능
1. 데이터 생성 및 송신 : 필요한 데이터를 연계 규격에 맞게 생성 후 전달
2. 데이터 변환 및 매핑 : 서로 다른 시스템 간 데이터 구조/컬럼명 일치
3. 데이터 수신 및 정제 : 받은 데이터를 검증하고 저장 가능하게 정리
4. 연계 데이터 관리 : 데이터 전송 형식과 저장 위치를 관리
5. 네트워크/프로토콜 관리 : 데이터가 안전하게 전달되도록 통신 규칙 관리

연계 요구사항 분석
- 개발 전 어떤 데이터를, 어떤 방식으로 주고받을 지 미리 분석하여 통합 구현의 설계 기반 자료를 마련하는 과정

현행 시스템 및 환경 파악 -> 사용자 요구사항 수집 -> 연계 데이터 분석
-> 결과 정리

입력물(Input)
시스템 구성도 : 하드웨어, 소프트웨어, 네트워크 연결 구조 문서
응용 어플리케이션 구성 :  화면 및 프로세스 흐름도
ERD

분석 도구 및 기법
인터뷰 & FGI : 핵심 사용자와 직접 대화(가장 정확하나 긴 시간이 소요됨)
체크리스트 : 성능, 보안, 주기 등 누락 방지용 점검 목록
설문 조사 : 다수 사용자의 의견 수집
델파이 기법 : 여러 전문가의 반복적인 의견 수집으로 전문성 확보
연계 솔루션 비교 : EAI, ESB, Open API 등의 장단점 비교

연계 데이터 식별 및 표준화
연계 데이터 식별의 개념
- 서로 다른 시스템이 주고받기 위해 필요한 데이터를 찾고, 동일한 기준으로 정의하는 과정
연계 데이터 식별이 필요한 이유
1. 데이터 구조와 코드 불일치 해결
2. 오류 예방 : 시스템별로 타입이나 길이가 달라서 데이터 누락
3. 변환과 검증 자동화 : 미리 변환 규칙을 정의하면 프로그램이 자동으로 처리할 수 있다.
4. 확장성과 유지보수성 확보 : 공통 기준을 사용하면 새로운 시스템이 추가되기 쉽다.
5. 성능과 보안 품질 확보 : 연계할 데이터와 형식을 미리 정의하면 불필요한 데이터 전송과 변환을 줄일 수 있다.

데이터 표준화
- 송/수신 시스템이 사용하는 서로 다른 데이터 구조, 컬럼명, 타입, 길이 코드 체계를 하나의 기준으로 맞추는 과정

표준화 절차
1. 연계 범위 및 항목 정의 : 어떤 데이터를 연계할지 결정
ㄴ 연계 대상 시스템, 연계 대상 테이블, 연계 대상 컬럼, 데이터 타입, 데이터 길이, 코드 사용 여부, 필수 여부
- 송신과 수신 시스템의 형식이 다를 경우 일반적으로 실제로 데이터를 사용하는 수신 시스템의 규격을 기준으로 변환한다

2. 코드 변환 및 매핑 : 송수신 시스템에서 사용하는 코드값이 다르면 변환 규칙을 정의한다

3. 연계 데이터 식별자 추가 : 수신 시스템은 전달받은 데이터가 어떤 원본 데이터인지 알아야 한다

4. 변경 구분 추가 : 전송된 데이터가 추가,수정,삭제 중 어떤 작업인지 알려줘야 한다.

5. 관리 정보 추가 : 연계 상태를 확인하고 모니터링 하기 위해 관리용 데이터를 추가한다

6. 데이터 표현 방식 정의 : 연계 데이터를 어떤 형식으로 전달할지 결정
ㄴ JSON, XML, CSV, ...

7. 인터페이스 정의서 및 명세서 작성 : 표준화한 내용을 공식 문서로 정리한다

인터페이스 정의서 : 시스템간 인터페이스 현황을 중심으로 작성

인터페이스 명세서 : 인터페이스별 실제 데이터 항목을 상세히 작성

연계 메커니즘 구성하기
연계 메커니즘 : 송신 시스템의 데이터를 수신 시스템까지 안전하고 정확하게 전달하기 위한 전체 기술 구조와 처리 절차

연계 메커니즘의 구성 요소
송신 시스템 : 데이터를 보내는 시스템
ㄴ 데이터 추출 : 운영DB에서 필요한 데이만 가져온다
ㄴ 데이터 생성 : 인터페이스 테이블, 파일 또는 메시지 형태로 가공
ㄴ 송신 로그 기록 : 보내려는 데이터의 처리 결과를 기록
ㄴ 오류 처리와 재전송 : 전송이 실패하면 실패 원인을 기록하고 다시 전송할 수 있도록 관리
수신 시스템 : 데이터를 받는 시스템
인터페이스 테이블 또는 파일 : 데이터를 임시로 보관하는 중간 저장소
연계 서버 또는 어댑터 : 데이터와 통신 방식을 변환하여 전달하는 중계자
로그 및 모니터링 : 처리 성공 실패와 오류 원인을 기록하고 감시하는 기능

연계 데이터 생성 및 추출
1. 추출 대상을 선정 : 모든 데이터를 보내는 것이 아니라 업무에 필요한 데이터만 추출
2. 추출 조건 결정 : 어떤 데이터를 추출할 것인지 조건을 정한다
WHEHE send_status = 'N'  신규데이터만 추출
WHERE update_date > :last_send_date : 특정 시간 이후 변경된 데이터 추출
WHERE order_status = 'PAYMENT_COMPLETE' 특정 업무 상태 데이터 추출
3. 추출 주기를 결정
실시간 : 데이터 발생 즉시 처리 -> 결제 승인, 주문 완료
분단위 : 몇 분마다 실행 -> 재고 현황
시간단위 : 한 시간마다 실행 -> 매출 집계
일단위 : 하루 한 번 실행 -> 일일 정산

추출방식
어플리케이션에 직접 생성
- 회원 가입이나 주문 완료 로직이 실행될 때 연계 데이터를 함께 생성한다
- 업무 상황에 맞는 데이터를 정확히 만들 수 있다는 장점이 있다.
별도 배치 프로그램
- 정해진 시간에 운영 DB를 조회하여 연계 데이터를 생성한다
- Trigger : 테이블에 데이터가 추가되거나 변경될 때 db가 자동으로 연계 데이터를 생성한다
- 다만 Trigger에 복잡한 로직을 많이 넣으면 db관리가 어려워질 수 있다.
CDC
- 운영DB에서 변경된 데이터만 찾아 실시간에 가깝게 추출하는 기술
- 따라서 대용량 환경에서 전체 테이블을 반복 조회하는 부담을 줄일 수 있다.

코드 매핑과 데이터 변환
송신 시스템과 수신 시스템은 같은 의미의 데이터를 서로 다르게 표현할 수 있다.
필드명 차이
orderId -> order_id

코드값 차이
송신코드 U
수신코드 USER
연계 프로그램이 U를 USER로 코드 매핑을 해준다

데이터타입 차이
송신시스템 : "1000" 문자열
수신시스템 : 1000 숫자
연계 서버에서 문자열을 숫자로 변환해야 한다

데이터 포맷 차이
송신 시스템 : JSON
수신 시스템 : XML
연계 서버가 JSON을 XML로 변환한다

인터페이스 테이블과 파일
송신 시스템과 수신 시스템 사이에서 데이터를 임시로 보관하는 중간 저장소
바로 운영DB에 저장하지 않고 중간에 보관하는 이유
- 데이터 검증 가능
- 오류 데이터 분리 가능
- 실패 데이터 재처리 가능
- 송신과 수신 시스템의 처리 시간을 분리 가능
- 대량 데이터 처리 가능
- 운영 DB 오염 방지

인터페이스 파일
DB 테이블 대신 파일을 사용할 수도 있다

- CSV
- JSON
- XML
- 고정 길이 텍스트

연계서버와 어댑터
송신 시스템과 수신 시스템 사이에서 통역사와 교통정리 역할을 하는 프로그램

송신시스템과 수신시스템을 직접 연결하면 송신 프로그램이 수신 시스템의 모든 구조를 알아야 한다.

쇼핑몰 -> ERP
쇼핑몰 -> 물류
쇼핑몰 -> 회계
쇼핑몰 -> CRM

연결 대상이 많아질수록 쇼핑몰 프로그램 안에 변환 코드가 계속 증가한다.

쇼핑몰 -> 연계 서버 -> ERP, 물류,회계,CRM

송신 시스템은 데이터를 보내주기만 하면 연계 서버가 각 시스템에 맞게 변환하여 전달합니다.

처리 결과 기록

실패 데이터 재처리
- 실패한 데이터는 정상 데이터와 분리한다
- 처음부터 1000건 모두 다시 처리하면 중복 저장 가능성이 있으므로 실패한 데이터만 정확하게 재처리해야한다.

로그
연계 과정에서 발생한 처리 이력과 결과를 시간순으로 기록한 데이터

로그가 필요한 이유
- 언제 문제가 발생했는지 확인
- 어느 단계에서 발생했는지 확인
- 어떤 데이터를 처리했는지 확인
- 원인이 네트워크인지 데이터인지 확인
- 성공 건수와 실패 건수 확인
- 재처리 대상 확인
- 감사와 보안 기록 보관
- 성능 병목구간 분석

로그의 종류
1. 시스템 로그
- 서버나 연계 엔진 자체의 문제를 기록한다
2. 연계 로그
- 특정 인터페이스의 송수신, 변환, 처리 상태를 기록한다
3. 데이터 로그
- 개별 행이나 필드 단위의 오류를 기록한다

일반 로그와 오류 로그
1. 통합방식
- 하나의 로그 테이블에 성공과 실패를 모두 기록한다
장점
한 테이블에서 전체 흐름 확인 가능
구조가 단순하다
단점
데이터가 매우 많아질 수 있다
오류만 빠르게 조회하기 불편할 수 있다
2.분리 방식
정상 처리 로그와 오류 로그를 따로 저장한다
장점
오류 조회와 분석이 쉽다
오류별 상세 정보를 별도로 관리 가능하다
단점
두 테이블의 관계를 함께 관리해야한다
전체 처리 흐름 조회가 복잡해 질 수 있다

연계 오류의 유형
연계 시스템 오류
서버 네트워크, 디스크 등 시스템 환경에서 발생하는 오류
- 인터넷 또는 전용선 끊김
- 서버 종료
- CPU 사용률 과다
- 메모리 부족
- 디스크 공간 부족
- DB 접속 실패
- 포트 차단
- 인증서 만료

해결 방법
- 서버 상태 점검
- 네트워크 연결 확인
- IP와 PORT 확인
- 서버 재기동
- 디스크 공간 확보
- 자원 증설
- 방화벽 정책 확인

연계 프로그램 오류
연계 프로그램ㅁ이나 변환 로직의 버그로 발생한다
- NullPointerException
- JSON 파싱 오류
- 날짜 변환 오류
- 코드 매핑 로직 오류
- SQL 문법 오류
- 파일 경로 오류
- 예외 처리 누락
해결방법
- 프로그램 로직 수정
- 예외 처리 추가
- 테스트 케이스 보강
- 수정 프로그램 배포
- 실패 데이터 재처리

연계 데이터 오류
데이터 자체에 문제가 있을 때 발생
- 이름이 NULL
- 전화번호 형식 오류
- 존재하지 않는 코드
- 데이터 길이 초과
- 숫자 필드에 문자 입력
- PK 중복
- 참조 데이터 없음
해결방법
- 원본 데이터 보정
- 코드 매핑 테이블 수정
- 데이터 재생성
- 검증 규칙 추가
- 정상화 후 재처리

장애 및 오류 처리 절차
1. 오류 모니터링
- 송신, 전송, 수신 구간의 로그를 수집한다
- 이메일 , SMS, 메신저, 운영 대시보드, 장애 알림 시스템같이 알림을 구성할 수 있다.

2. 오류 식별
- 어느 인터페이스인지
- 어떤 데이터인지
- 어느 처리 단계에서 실패했는지
- 오류 코드가 무엇인지
- 정상 데이터와 무엇이 다른지
- 반복적으로 오류가 발생하는지
확인한다

3. 오류 원인 분석
- 송신 시스템 로그, 연계 서버 로그, 수신 시스템 로그, 운영 DB로그를 비교한다
- 네트워크 문제라면 IP, Port, 접속 가능 여부, 방화벽, 인증서, 응답시간을 확인한다
- 데이터 문제라면 각 필드값을 비교한다

4. 해결 방안 결정
- 수동 재전송
- 자동 재전송
- db 롤백
- 데이터 보정
- 프로그램 수정
- 서버 설정 변경
- 네트워크 설정 변경

6. 정상 처리 여부 확인
- 로그가 success로 변경되었는가?
- 수신 i/f테이블에 저장되었는가?
- 운영 db에 정상 반영되었는가?
- 중복 데이터가 없는가?
- 사용자 화면에서도 정상적으로 보이는가?

재처리 설계 시 주의점
실패한 작업을 단순히 다시 실행하면 중복 데이터가 발생할 수 있다.
수신 시스템에서 원본 키를 확인하여 이미 처리한 주문이면 등록하지 않는다.

연계 메커니즘 정의서
각 연계 구간을 어떤 방식으로 구현할지 결정할 공식 설계 문서
정의서에는 다음과 같은 항목을 포함한다
영역,구간 : 송신,전송,수신,db반영
구성 요소 : API, I/F테이블, 파일, 연계 서버
구현 방식 : 실시간, 배치, 메시지 큐
고려 요소 : 데이터량, 보안, 성능, 오류 처리
결정사항 : 실제 적용할 구체적인 방식

- 반영 주기가 정해졌는가?

최신 연계 방식의 흐름
- 과거 연계 방식이 파일과 배치 중심이었다면, 최근에는 실시간 API, 메시지 큐, 이벤트 스트리밍, 통합 모니터링 중심으로 발전하고 있다.

API GateWay : 여러 시스템이 제공하는 API 앞에 위치하여 API 요청을 한 곳에서 받아 적절한 시스템으로 전달하는 중간 관문

장점
- 각 서비스마다 인증과 보안 코드를 별도고 구현하지 않고 게이트웨이에서 공통적으로 처리할 수 있다.
- 외부에는 실제 내부 서버 주소를 노출하지 않아도 된다.

Kong
여러 api 앞에 설치하여 요청을 관리하는 API Gateway 및 api 관리 도구
장점
- 가볍고 처리 속도가 빠르다
- 플러그인 방식으로 기능을 추가할 수 있다
- 오픈소스 버전과 사용버전이 존재한다
단점
- 인증,라우팅,플러그인 설정이 많아지면 관리가 복잡해진다.
- API Gateway에 업무 로직까지 넣으면 구조가 복잡해질 수 있다.

apigee
- 구글 클라우드에서 제공하는 기업용 API 관리 플랫폼
- 단순히 요청을 전달하는 게이트웨이 기능뿐만 아니라 API의 설계, 배포, 보안, 사용량 분석, 개발자 공개까지 API 전체 생명주기를 관리한다

장점
- 대규모 기업 API를 중앙에서 관리하기 좋다
- API 분석과 보안 관리 기능이 강력하다
- 구글 클라우드 서비스와 연계하기 좋다

단점
- 소규모 시스템에는 기능과 구조가 과다할 수 있다
- 사용량과 구성에 따라 비용이 커질 수 있다.

NGINX
본래 웹 서버, 리버스 프록시, 로드 밸런서의 역할을 하나 요청을 받아 여러 API 서버로 전달하고, 인증, 속도 제한, 보안 정책을 적용할 수 있어 API Gateway역할로도 사용된다.

장점
- 웹 서버와 프록시 분야에서 널리 사용된다
- 처리 성능이 우수하다
- 설정 파일 기반이라 구조가 비교적 단순하다

단점
- 기본 nginx만으로는 완전한 api 관리 플랫폼 기능이 부족하다
- 설정 파일이 커지면 관리하기 어렵다
- 설정 오류가 여러 api에 영향을 줄 수 있다

WSO2
API의 생성, 공개, 구독, 보안, 제한, 통계 등을 관리하는 API관리 플랫폼

장점
- API 전체 생명주기를 관리할 수 있다.
- 오픈소스 기반 선택지가 있다

단점
- 구성 요소가 많아 설치와 운영이 복잡할 수 있다.
- Java 기반 기업 환경에 익숙하지 않으면 학습 부담이 있다.

GraphQL
필요한 데이터의 항목을 직접 지정하여 요청하는 API 질의 방식이다

장점
- 필요한 데이터만 요청할 수 있다
- 여러 관련 데이터를 한 번에 조호할 수 있다.

단점
- 서버 구현이 REST보다 복잡할 수 있다
- 복잡한 중첩 질의가 DB에 큰 부하를 줄 수 있다

gRPC
원격 서버의 메서드를 같은 프로그램의 메서드처럼 호출할 수 있게 해주는 고성능 RPC(Remote Procedure Call) 기술이다

장점
- 데이터 크기가 작고 처리 효율이 높다
- 여러 프로그래밍 언어를 연결하기 좋다

단점
- 브라우저에서 직접 사용하려면 추가 구성이 필요하다
- postman과 단순 http 도구 중심의 테스트보다 복잡할 수 있다

Kafka
대량의 이벤트를 실시간으로 저장하고 전달하는 분산 이벤트 스트리밍 플랫폼

장점
- 대량의 이벤트를 빠르게 처리할 수 있다
- 이벤트를 일정 기간 저장하여 다시 읽을 수 있다
- 장애가 발생해도 복제된 데이터를 통해 복구할 수 있다

단점
- 클러스터 설치와 운영이 어렵다
- 중복 이벤트에 대비해야 한다
- 소규모 메시지 전송에는 과도할 수 있다

Pulsar
Kafka와 비슷한 분산 메시징 스트리밍 플랫폼

장점
- 여러 조직이나 서비스를 분리하여 관리하기 좋다
- 여러 지역의 클러스터 간 메시지 복제에 유리하다

단점
- Kafka보다 국내외 개발자 자료와 운영 경험을 찾기 어려울 수 있다.

Event Hub
- 마이크로소프트 Azure에서 제공하는 완전 관리형 이벤트 스트리밍 서비스

장점
- 서버와 클러스터를 직접 관리할 필요가 없다
- 자동 확장 모니터링 기능을 활용할 수 있다

단점
- Azure 플랫폼에 의존한다
- 지속적인 사용 비용이 발생한다

MuleSoft
서로 다른 어플리케이션, 데이터베이스, API, 클라우드 서비스를 연결하는 기업용 통합 및 API 관리 플랫폼

장점
- 복잡한 기업 시스템 연계에 적합하다
- 다양한 사전 제작 커넥터를 제공한다
- API 관리와 시스템 통합을 한 플랫폼에서 처리할 수 있다

단점
- 제품과 라이선스 비용이 높을 수 있다
- 플랫폼 학습 범위가 넓다

Boomi
어플리케이션, 데이터, api, 업무 흐름을 연결하는 클라우드 네이티브 iPaaS

장점
- gui 방식으로 비교적 빠르게 연계를 만들 수 있다
- 클라우드와 내부 시스템을 함께 연결할 수 있다
- 개발 코드의 양을 줄일 수 있다

단점
- 복잡한 업무 로직은 별도 코드가 필요할 수 있다
- 대량 성능 터리를 세밀하게 조정하는 데 한계가 있을 수 있다

SnapLgoic
데이터와 어플리케이션을 연결화는 시각적 iPaaS플랫폼

장점
- 블록을 연결하는 방식이라 흐름을 이해하기 쉽다
- 어플리케이션 통합과 데이터 통합을 함께 지원한다

단점
- 플랫폼 사용료가 발생한다
- 직접 코드로 구현하는것 보다는 세밀한 제어가 어려울 수 있다.

Informatica
기업의 데이터를 추출하고, 변환하고, 이동하고, 품질을 관리하는 데이터 통합 및 데이터 관리 플랫폼

장점
- 대규모 기업 데이터 통합에 적합하다
- 데이터 품질과 메타데이터 관리 기능을 함께 사용할 수 있다.

단점
- 제품 구조와 기능이 복잡하다
- 라이선스 운영 비용이 높을 수 있다.
