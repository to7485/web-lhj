화이트 박스 테스트
- 프로그램의 소스 코드, 내부 로직, 제어 흐름, 조건문, 반복문을 확인하면서 수행하는 테스트
- 테스트 담당자가 프로그램 내부 구조를 알고 있다는 전제에서 진행한다.

블랙 박스 테스트
- 프로그램의 내부 소스코드나 구조를 보지 않고, 입력값을 넣었을 때 기대한 출력값이 나오는지 확인하는 테스트
- 사용자 요구사항에 따라 기능이 정확하게 동작하는지 확인

드라이버
- 상향식 테스트에서 아직 개발되지 않은 상위 모듈을 대신하여 하위 모듈을 호출하는 임시 프로그램

스텁
- 하향식 테스트를 수행할 때 아직 개발되지 않은 하위 모듈을 대신하는 임시 프로그램

1.
- V 모델은 소프트웨어 개발 단계와 테스트 단계를 서로 대응시켜 개발과 테스트를 함께 계획하는 개발 모델이다
- 각 개발 단계에서 만든 산출물이 올바르게 구현되었는지 대응되는 테스트를 통해 검증하기 때문이다.
요구분석 -> 인수 테스트
아키텍처 설계 -> 시스템 케스트
모듈 설계 -> 통합 테스트
구현 -> 단위 테스트

2.
단위 테스트
목적 : 하나의 기능이나 모듈이 정상적으로 동작하는지 확인한다
대상 : 메서드, 클래스, 서비스 등 작은 단위
수행자 : 개발자

통합 테스트
목적 : 모듈 간 연결과 인터페이스가 정상적으로 동작하는지 확인
대상 : 컨트롤러, 서비스, DAO 등의 연결
수행자 : 개발자 또는 테스트 담당자

시스템 테스트
목적 : 전체 시스템이 요구사항에 맞게 동작하는지 확인한다
대상 : 전체 시스템
수행자  : 테스트 팀

인수 테스트
목적 : 실제 업무에 사용할 수 있는지 확인한다
대상 : 실제 업무 절차
수행자 : 사용자 또는 고객

3.
구조 기반 테스트
기준 : 프로그램 내부 구조
코드 확인 : 확인함
종류 : 화이트박스 테스트
목적 : 제어 흐름과 조건 검증

명세 기반 테스트
기준 : 요구사항과 명세
코드확인 : 확인하지 않음
종류 : 블랙박스 테스트
목적 : 입력과 출력 및 요구사항 검증

4.
상향식 : 하위 모듈 부터 상위 모듈 방향으로 결합하여 테스트 하는 방법
하향식 : 상위 모듈 부터 하위 모듈 방향으로 결합하여 테스트 하는 방법
Driver : 아직 개발되지 않은 상위 모듈을 대신하여 하위 모듈을 호출하는 임시 프로그램
Stub : 아직 개발되지 않은 하위 모듈을 대신하여 미리 준비한 결과를 반환하는 임시 프로그램

5.
사용자 인수 테스트
수행자 : 업무 담당자, 고객
확인 내용 : 업무 절차와 요구사항 충족 여부
운영상의 인수 테스트
수행자 : 시스템 운영자, 관리자
확인 내용 : 백업, 복원, 장애 복구, 계정 관리
계약 인수 테스트
수행자 : 발주사와 개발사
확인 내용 : 계약서와 요구사항 충족 여부
규정 인수 테스트
수행자 : 품질 담당자, 감사 담당자
확인 내용 : 법규, 보안, 산업 표준 준수 여부
알파 테스트
수행자 : 개발 조직 내부 직원
확인 내용 : 내부 환경에서 제품 품질 확인
베타테트스
수행자 : 실제 사용자
확인 내용 : 실제 환경에서 사용성 및 문제점 확인

1.
B : 장애가 발생하면 고객이 주문을 완료할 수 없으므로 업무 중요도와 장애 영향도가 높다
C : 하루 평균 20만 회 사용되는 기능이므로 사용 빈도가 매우 높아 테스트  우선 순위가 높다
E : 최근 수정되었으며, 결제 시스템과도 연계되므로 변경으로 인한 결함 발생 가능성과 외부 시스템 연계 위험을 고려하여 먼저 해야한다

2.
통합테스트를 시작하면 안된다.

테스트 케이스에 대한 검토가 완료되지 않았으므로 테스트 케이스를 검토해야 한다.
결제 연동 모듈 오류가 있으므로 해당 오류를 수정한 후 정상적으로 실행되는지 확인해야 한다.

3.
정상 카드를 이용하여 결제를 요청한다 -> 카드 결제가 승인되고, 주문 완료 화면으로 이동해야 한다.

카드사에서 승인을 거절하도록 설정된 카드로 결제를 요청한다 -> 결제가 실패하고 주문이 완료되어서는 안된다.

정상 카드로 결제를 완료한다 -> 결제 성공 후 해당 주문 정보가 DB에 정상적으로 저장되어야 한다

결제버튼을 연속으로 여러 번 클릭한다 -> 하나의 주문에 대해 결제가 한 번만 처리되어야 하며 중복 주문 또는 중복 결제가 발생해서는 안된다

4.
- 테스트 과정에서 실제 고객 데이터가 변경되거나 삭제될 수 있다.
- 실제 고객의 이름, 전화번호, 주소 등의 개인정보가 테스트 담당자에게 노출될 수 있다.
- 테스트 주문이나 결제가 실제 매출에 반영되거나 테스트 문자가 실제 고객에게 발송될 수 있다.

이를 방지하기 위해 실제 운영 데이터를 직접 사용하는 대신, 별도의 운영 데이터를 테스트 환경으로 복사하고 개인정보를 마스킹하여 테스트 데이터로 사용해야 한다.

5.
A는 화면 모듈에서 확인해야 한다. 버튼 동작이랑 이벤트를 확인해야 한다.
B는 데이터 입출력을 확인해야 한다. DB에 실제 저장된 전화번호가 잘못됐으니까
C는 인터페이스를 확인해야 한다. 요청 데이터 형식이 잘못되었으므로 시스템 간 데이터 전달 및 변환 부분을 확인해야 한다
D는 서버 모듈을 확인해야 한다. 나이를 계산하는 로직이 잘못됐으니까

6.
통합테스트 종료하면 안된다.
B는 개인정보가 다른 사용자에게 노출되는 결함으로 보안 및 개인정보 보호에 중대한 영향을 미치므로 테스트를 종료할 수 없다
D는 카드 결제가 전혀 처리되지 않는 결함으로 쇼핑몰의 핵심 업무인 결제가 수행되지 않으므로 테스트를 종료할 수 있다

테스트 종료는 모든 결함이 제가되었는지만 보는게 아니라 남아있는 결함의 중요도와 운영 위험을 고려하여 판단해야 한다

7.
TPS 목표는 350TPS 가 측정되었으므로 충족
응답 목표는 3초인데 실제 5.8초로 미충족
CPU사용량 목표가 80%이하인데 실제는 96%로 미충족

시스템 전체의 성능 목표를 충족했다고 판단할 수는 없다.

8.
병목지점 : 주문 조회 데이터베이스 쿼리
800만건의 데이터가 존재하고 주문번호 검색에 인덱스가 없으며, 실제 SQL 실행 시간이 4.2초로 평균 응답시간 5.8초중 큰 비중을 차지하고 있다.

따라서 주문번호 검색 컬럼의 인덱스 적용 및 SQL쿼리 최적화 등의 튜닝을 수행한 후 동일한 조건으로 성능 테스트를 다시 수행하여 TPS, 응답시간, CPU 사용률이 목표치를 만족하는지 확인해야 한다
