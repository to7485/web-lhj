2. 애플리케이션 배포 환경 설정
2-1. 애플리케이션 배포 단위
- jar(Java Archive)
ㄴ Java 라이브러리, 리소스, 설정파일 들을 포장한다.
- war(Web Archive)
ㄴ 웹 컨테이너에 배포, Servlet, jar파일, WEB-INF 안에 있는 web.xml파일로 구성

web.xml : 웹 애플리케이션이 실행될 때 WAS가 가장 먼저 읽는 설정 파일

- ear(Enterprise Archive)
ㄴ jar와 war를 묶어서 하나의 완성된 웹 애플리케이션 서비스를 제공

2-2. 형상관리 시스템
- 형상관리의 범위
ㄴ 신규 프로젝트 및 보완 개발, 업무 시스템의 운영/유지 보수, 전산 설비 및 시스템 소프트웨어 등과 관련된 작업, 사용자 파일 관리
- 형상관리 시스템에서 사용하는 용어
ㄴ 형상관리 : 소프트웨어 전체 생명 주기를 지속적으로 관리하는 것
ㄴ 형상항목 : 관리의 대상이 되는 항목, 소스파일, 문서, 기타 사항
ㄴ 기준선 : 공식적으로 검토되고 협의되어 향후 기준이 되는 형상 항목의 집합체
ㄴ 마이그레이션 : 개발 완료된 시스템이 운영 단계로 전환될 때 관련 소스 파일을 저장공간으로 이관시키는 작업
ㄴ 리포지터리 : 관리 대상을 일괄 전송하여 압축, 암호화한 후에 저장, 관리하는 저장공간을 의미
ㄴ 워크플로 : 형상관리 활동을 수행하기 위해 미리 정해진 절차
ㄴ 반출(Check Out) : 형상 항목을 수정하기 위해 리포지터리로부터 전송받는것
ㄴ 반입(Check In) : 반출된 형상 항목을 변경 후 다시 형상 리포지터리로 전송하는 것

1. 코드 인스펙션
- 정적 테스트의 가장 일반적인 유형으로, 사전에 정의된 코드 작성 규칙 기반으로 소스 코드를 점검하여 작성 규칙에 위반되는 소스코드를 추출하는 분석 도구
- 코드 인스펙션 Rule 유형
ㄴ 성능 개선 : 성능에 영향을 미칠 수 있는 코드 점검(메모리 누수, 미사용 변수, 메서드 여부 등)
ㄴ 코드 작성 규칙 :개발 언어의 문법, 프로젝트 내에서 정의된 명명 규칙의 준수 여부
ㄴ 에러 발생 가능성 : 애플리케이션 동작 중 에러 발생 가능성이 있는 코드를 점검
- 코드 작성 Rule 심각도 구분
ㄴ 필수, Blocker : 에러 발생 가능성이 매우 높거나 메모리 누수가 발생하는 코드로, 반드시 수정되어야 하는 위반 사항
ㄴ 권고 상, Critical : 에러 발생 가능성이 높거나 일반적으로 수정되어야 하는 심각한 위반 사항
ㄴ 권고 중, Major : 에러 발생 가능성이 있거나 수정을 권고하는 중요 위반 사항
ㄴ 권고 하, Minor : 소스코드의 가독성, 유지보수성 향상을 위해 수정을 권고하는 위반사항
ㄴ 정보, Info : 정보성으로 제공되는 위반 사항으로 개발자가 참고하여 적용할 수 있다.

- 정규 표현식 : 특정한 규칙을 가진 문자열의 집합을 표현하는 범용적인 방식

어떤 Test가 실패했는가

개발 중간에 발생한 문제를 늦게 발견할 수 있고, 수정에 필요한 비용과 시간이 증가하기 때문이다

적절하지 않다

실패한다면 리팩터링 과정에서 기존 기능이 변경되었을 가능성을 확인해야 한다.

기존 프로그램 -> 기존 Test 실행 -> Test 성공 확인 -> 리팩토링 -> 기존 Test다시 실행 -> 성공 -> 기존 동작 유지 확인
	     -> 실패 -> 변경 내용 분석 및 수정

프로그램 변경 후 기존 기능을 재검증하기 위한 중요한 자산으로 지속적으로 관리해야 한다.
